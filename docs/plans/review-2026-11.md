# Plan: the review of November 2026 (14 tasks)

This plan was written after a review of the whole app. It is made to be carried out one task at a time, by a model that has not seen the review. Everything you need to know that is not in the code is written here. When this plan and the code disagree, the code is right: stop and say so.

The owner does not write code and is answered in **Danish**. Everything in the app, the code and the docs is in **English**.

## Before you start any task

1. Read `CLAUDE.md` in the root, `docs/AREAS.md`, and the `CLAUDE.md` of the area the task names. Do **not** read all of `docs/DECISIONS.md` (it is 244 KB; task 7 fixes that): search it with grep for the words of your task.
2. One task = one branch from `main`: the branch name is given in the task. Do not mix tasks.
3. `git status` must be clean before you branch. If it is not, stop and tell the owner (an earlier task was left uncommitted).
4. Do the task exactly as written. If you need to change a file the task does not name, stop and say which file and why.
5. When the task is built, run the checks (below), then `pnpm areas report main --plan "<the areas of the task>"` and show the result. Explain every file that is outside the plan.
6. **Do not commit, merge, push or tag until the owner says so.** When they do: Conventional Commits, merge with `--no-ff`, never force, never reset.
7. Tick the task off in the list at the bottom of this file in the same commit.

### Checks (all must be green before you say a task is done)

```bash
source ~/.nvm/nvm.sh && nvm use 22
pnpm format:check && pnpm areas check && pnpm lint && pnpm typecheck && pnpm test
# Rust, only when a file under src-tauri/ changed. On the owner's computer it runs in a container:
distrobox enter mimer-dev -- bash -lc 'cd src-tauri && cargo fmt --check && cargo clippy --all-targets -- -D warnings && cargo test'
```

`pnpm exec prettier --write <files>` fixes formatting. `cargo test` also rewrites `src/bindings/`; commit those files when they change and never edit them by hand.

### Rules that are easy to break

- No raw `<button>`, `<input>`, `<textarea>`, `<select>` outside `src/components/`: use `Button`, `PlainButton`, `Input`, `InlineInput`, `Checkbox`, `Radio`, `Textarea`, `Select`. Lint fails otherwise.
- One React component per file for new code. Tests sit next to the code (`Foo.tsx` + `Foo.test.tsx`) and mock `@/lib/api`.
- Every backend call goes through `src/lib/api.ts`. A new Tauri command is registered in `src-tauri/src/lib.rs` and gets a typed wrapper in `api.ts`.
- Rust: no `unwrap`, `expect` or `panic!` outside tests. Commands in `src-tauri/src/commands/` are thin; logic lives in the area's module and is tested there with `tempfile`.
- A choice kept per computer is browser storage wrapped in try/catch (`src/lib/safeStorage.ts`), and the screen must work without it.
- Never put a local path, a user name or a real note in anything committed. Screenshots come only from the demo vault, in a headless browser. Never drive the owner's desktop.
- Colours come from the theme tokens (`bg-card`, `bg-accent`, `text-muted-foreground`, …). `bg-popover` does **not** exist in Mimer; a floating list uses `menuContent` from `src/components/ui/menuStyles.ts`.
- A dialog opened from the editor toolbar: the toolbar cancels mouse presses to keep the editor's focus. `DialogContent` already stops that (see `src/components/ui/dialog.tsx`); any other floating thing you add inside the toolbar's React tree needs the same care.
- A user-visible change updates `CHANGELOG.md` under `[Unreleased]` (short, what the person can now do), `docs/MANUAL_TESTS.md`, the help topic in `src/features/help/topics/` and, for a new rule, `docs/DECISIONS.md` (add a row at the bottom; after task 7, in the new short file).
- `docs/shared-facts.json` lists sentences that `README.md` and `site/index.html` must both contain word for word (`src/lib/sharedFacts.test.ts`). If you change one of them, change it in all three places.

## Task 4: backup of a vault

**Kind:** new function. **Areas:** History (`src-tauri/src/git/`), Settings and help, App shell (status bar). **Branch:** `feat/vault-backup`. **Design:** board 27, card A. **Use the larger model, or check each step with the owner.**

**Why:** every vault is a Git repository inside the vault's own folder. If the disk fails, the notes and their whole history are gone. A backup is a second copy of the repository in a folder the person chooses (an external disk, or a folder another program syncs). Nothing is sent anywhere by Mimer.

**What the person sees:** **Settings → Vault** gets a part **Backup**: a line of explanation ("A copy of your notes and their whole history in another folder: an external disk, or a folder that is synced."), **Backup folder** with **Choose…**, a button **Back up now**, a line with the result ("Backed up today 09:12", or the error), and a box **Back up when Mimer closes**. When a backup folder is set and the last backup is more than 7 days old (or failed), the status bar shows a small warning "Backup is 9 days old" that opens the setting.

**Decisions already made (do not change without asking):**

- The backup is a **bare Git repository** at `<backup folder>/<vault name>.git`. It is made the first time. A backup is: flush and commit what is unsaved (the same snapshot commit the app makes when it closes a vault), then push every local branch to it. Use the `git2` crate that the app already has; a push to a local path needs no network and no credentials.
- It never forces. If the push is refused because the backup has commits the vault does not have, the backup is left alone and the person is told: "The backup folder holds another history. Choose an empty folder."
- The settings are **per computer and per vault**, in the global settings file (`src-tauri/src/settings/mod.rs`), not in `.vault/config.json` (that file is committed, and a folder path must not be). New field on `Settings`: `backups: HashMap<String, VaultBackup>` keyed by the vault's path, with `folder: String`, `on_close: bool`, `last_ok: Option<String>` (RFC 3339) and `last_error: Option<String>`. `#[serde(default)]`, so old settings files still load. `schemaVersion` stays 1.
- Restoring is not a screen in this task. The help text says how: copy or `git clone` the `.git` folder from the backup to a new place and open it as a vault. Before writing that sentence, try it in a test: clone the bare repository with `git2` and check the notes are there.
- Files that Git does not track (look at the vault's `.gitignore`: chats, the embedding index) are not in the backup. Say so in the help text.

**Do:**

1. `src-tauri/src/git/backup.rs`: `pub fn backup(vault: &OpenVault, folder: &Path) -> AppResult<BackupReport>` (`BackupReport { path: String, commits: u32 }` or similar, derive `TS`). Tests with two temp folders: first backup makes the bare repository and it has the commits; a second backup after a change adds the new commit; a backup folder with a foreign history is refused and unchanged; a folder that does not exist gives a clear error.
2. Commands (thin) in `src-tauri/src/commands/git.rs`: `backup_now()` (reads the folder from the settings for the current vault, runs the backup, stores `last_ok` or `last_error`, saves the settings), and the settings are changed through the existing settings save. Register, add `api.backupNow`.
3. On close: where the vault is closed and the last commit is made (`vault::session`), run the backup when `on_close` is set. A failure must never stop the app from closing: store the error and go on.
4. Frontend: `src/features/settings/BackupSettings.tsx` in the Vault tab (`VaultSettingsTab.tsx`), with the folder dialog the app already uses (`@tauri-apps/plugin-dialog` through `src/lib/dialogs.ts`). A small pure function `backupAge(lastOk, now)` in `src/lib/backup.ts` (add the path to the Settings and help row in `docs/AREAS.md`) gives the text for the status bar; test it. `src/components/layout/StatusBar.tsx` shows the warning.
